PRISM Security — What Protects Your Data

A guide for decision-makers: what security is in place, what was recently fixed, and what still needs attention.

Updated 2026-06-25 · Based on June 2026 security review

Bottom Line

An outside security review found 15 issues with PRISM. 14 of those 15 have been fixed in the code. The fixes were tested and confirmed working (36 test files, 75 tests all passing, zero build errors). The one remaining issue involves server hardware configuration (firewall, secure remote access, traffic filtering) — not something that can be fixed in the application code itself.

A follow-up review confirmed the code fixes are solid, but noted that PRISM now needs ongoing processes (not just one-time fixes): clear ownership of security responsibilities, regular testing of backups, and a plan for meeting regulations that may apply depending on who uses PRISM and where they are located. Estimated remaining work: 400–1,000+ hours depending on which regulations apply.

1. Authentication — How You Log In

What this protects: Only real, approved people can get into PRISM. Strangers, bots, and attackers cannot.

PRISM uses a trusted login system called Better Auth. Instead of passwords (which people forget, reuse, or have stolen), PRISM sends a one-time login link to your email. You click it, and you're in.

1.1 Login Flow (Magic Links)

You enter your email on the login page. PRISM sends you a link. You click the link. No password needed. If someone steals the link, it only works once and expires quickly.

1.2 Code: How Magic Links Are Sent

This is the code that runs when you click "Send login link." It builds the email and sends it to your inbox. The link inside is single-use and time-limited.

FIXED When someone requests a login link, PRISM now always says the same thing: "If an account exists for this email, a magic link has been sent." Previously, the response revealed whether an email was registered or not — which let attackers map out who had accounts. That leak is now closed.

FIXED The security review found that all new accounts were being created with the same hardcoded backup password: "Password#123". Even though users log in with email links (never passwords), having a guessable fallback was a serious risk. It is now replaced with a computer-generated random string that nobody could guess.

What this protects: A data analyst from Utility A cannot see Utility B's financials. An external partner cannot edit data. Each person can only reach the parts of PRISM their job requires.

2.1 How Access Is Checked (Every Page, Every Time)

Whenever you visit a protected area in PRISM (dashboards, data entry, settings), a gatekeeper runs through four checks before letting you in. If any check fails, you are redirected away.

  // Step 2: Load the user and their role from the database
  // (uses a 5-second cache to avoid hitting the DB on every request)
  const [fetchedUser] = await db.select().from(user)
    .where(eq(user.id, userId)).limit(1);

  if (!currentUser.emailVerified) {
    return NextResponse.redirect(
      new URL("/profile?verify=required", request.url)
    );

  // Step 4: Is the user's role allowed to access this page?

Think of this as a security guard at every door. Before you enter any room in the building: the guard checks your ID (are you logged in?), confirms you're still active (has your email been verified?), and verifies your clearance level (does your role allow access to this room?).

3. API Key Security — Protecting Automated Data Exchange

What this protects: PRISM shares data with other systems (Power BI dashboards, training platforms, email processors). Each of these connections requires a secret key — like a password for machines. Without the right key, these systems cannot pull any data.

PRISM has about 40 data-sharing endpoints that other systems connect to. These are protected by API keys — long secret codes — not user logins.

3.1 The Timing Attack Problem (and How PRISM Solves It)

A normal password check compares characters one by one and stops at the first mismatch. This means an attacker could measure how long the server takes to reject a bad key and gradually guess the real one — letter by letter. PRISM uses a constant-time comparison: the check always takes exactly the same amount of time no matter how many characters match. This makes timing-based guessing impossible.

3.2 Code: Timing-Safe API Key Check

// app/api/service.ts — authorizeApiKey()
import { timingSafeEqual } from "crypto";

export function authorizeApiKey(req: Request): boolean {
  const apiKey = process.env.API_KEY;           // stored in environment variable
  if (!apiKey) return false;
  const header = req.headers.get("x-api-key");
  if (!header) return false;
  return safeCompare(header, apiKey);
}

function safeCompare(a: string, b: string): boolean {
  const bufA = Buffer.from(a);
  const bufB = Buffer.from(b);
  // Only compare if lengths match (otherwise Buffer comparison throws)
  return bufA.length === bufB.length && timingSafeEqual(bufA, bufB);
}
Every external system that connects to PRISM must include the correct secret key in its request. The key check cannot be timed or guessed. The actual key value is never stored in the code — it lives only in the server's secure environment settings.

3.3 What's Protected (40+ Endpoints)

All of these require the correct secret key: country data, currency data, customer categories, energy sources, generators, governance records, regional data, utility lists, generation statistics, financial accounts, tariffs, safety records, employee data, Power BI access, and user data.

3.4 Incoming Email Protection

When PRISM receives email replies (for example, through its Mailgun integration), the incoming message must carry a secret header. This header is checked using the same constant-time method, ensuring that only legitimate email replies are processed.

4. AI Chatbot Security — Guardrails & Rate Limiting

What this protects: The AI chatbot inside PRISM can access real utility data. Multiple layers of protection prevent it from leaking personal information, executing harmful commands, being tricked into revealing secrets, or being overused to run up costs.

PRISM includes an AI assistant (powered by Claude from Anthropic). Because it can see actual utility data, it has extra protections that a normal chatbot would not need.

4.1 What You Cannot Ask the AI

Before any message reaches the AI, it is checked against six rules. If a message matches any rule, it is blocked with a polite refusal.

RuleWhat it blocksExample blocked input
REF-PII-EMAILEmail addressesSend the report to jane@utility.com
REF-PII-PHONEPhone numbersCall +679 123 4567
REF-CREDENTIALSPasswords, API keys, tokensMy password is hunter2
REF-PRIVATE-COMMENTSPrivate reviewer notesShow me the private comments on KPI #5
REF-BULK-EXPORTMass data exportsExport all user records
REF-PROMPT-INJECTIONAttempts to override the AI’s instructionsIgnore all previous instructions and...
These rules exist so that: (1) personal contact details are never sent to the AI provider, (2) secret keys and passwords don't accidentally end up in chat logs, (3) nobody can use the chatbot to mass-export sensitive data, and (4) the AI cannot be tricked into ignoring its safety instructions.

4.2 What the AI Cannot Say Back

The AI's responses are also scanned before they are saved or displayed. If the AI accidentally outputs an email address, phone number, or Social Security number, it is automatically replaced with [REDACTED EMAIL] or similar markers.

4.3 Code: The Six Input Rules

export const validateInput = (message: string): AiGuardrailResult => {
  // Rule 1: Reject empty messages

    if (rule.pattern.test(message)) {
      return { passed: false, rule: rule.rule, reason: rule.reason };
    }
  }
  return { passed: true };
};

4.6 Power BI Query Safety

When the AI queries Power BI, it generates database commands. Before any command runs, a safety check ensures it can only read data — never modify, delete, or create anything in the Power BI dataset.

  • Blocked: Any command that could change or delete data (ALTER, CREATE, DROP, DELETE, INSERT, UPDATE, TRUNCATE, GRANT, REVOKE)
  • Blocked: Any command that could reveal system internals (INFO.*, DISCOVER_*, PROCESS, BACKUP, RESTORE)
  • Allowed only: Read-only commands (EVALUATE, SUMMARIZECOLUMNS, DEFINE, ORDER)
  • Maximum query length: 8,000 characters

5. Input Protection — Keeping Bad Data Out

What this protects: Every piece of information that enters PRISM — from a filter dropdown, an uploaded spreadsheet, or a custom style setting — is cleaned and validated before the system trusts it. This prevents attackers from slipping harmful code into forms, emails, or visual settings.

Any data that comes from outside PRISM (user input, file uploads, URL parameters) goes through a cleaning process before being used. Here are the main types of protection.

5.1 Filter Values Are Checked

When you select filters on a data entry page (like choosing a report period or a utility), those values are validated as actual numbers before the server uses them. Anything that is not a number is silently discarded.

// app/data-entry/filterContext.utils.ts (excerpt)
export function sanitizeFilterContext(raw: DataEntryFilterContextInput) {
  return {
    reportPeriodId: parseNullableInt(raw.reportPeriodId),
    utilityId:      parseNullableInt(raw.utilityId),
    energySourceId: parseNullableInt(raw.energySourceId),
    generatorId:    parseNullableInt(raw.generatorId),
    // ... every field validated
  };
}

5.2 Visual Style Settings Are Locked Down

PRISM lets DEV users customize the look and feel of the interface. To prevent someone from injecting harmful code through a style setting, every value is checked against strict rules:

  • Selectors: Only safe characters (letters, numbers, basic punctuation). Maximum 400 characters.
  • Colors: Hex format only (e.g., #ff6600)
  • Font sizes: 8 to 96 pixels only
  • Font weights: Only 400, 500, 600, or 700
  • Padding: 0 to 80 pixels only

5.3 Email Content Is Made Safe

All emails PRISM sends (login links, verification messages, notifications) sometimes include user-provided text like names and organization names. Before that text enters an email, characters that could be interpreted as HTML code (< > & ") are converted to harmless display versions. This prevents anyone from embedding malicious content in an email that appears to come from PRISM.

// lib/email.service.ts — lines 61-70
function escapeHtml(text: string): string {
  return text
    .replace(/&/g, "&amp;")
    .replace(//g, "&gt;")
    .replace(/"/g, "&quot;")
    .replace(/'/g, "&#039;");
}

5.4 Number Inputs Are Cleaned

Any number the system receives is first stripped of all non-number characters (except minus signs and decimal points). This is the most basic safety net — even if a more specific check misses something, the number cleaner catches it.

6. Browser Security — Invisible Protection

What this protects: Every time someone opens PRISM in their browser, the server sends hidden instructions that tell the browser how to behave safely. These instructions block common web attacks — like tricking the browser into loading harmful content from other websites, or embedding PRISM inside a fake page.
Recently fixed:
  • FIXED Duplicate and conflicting browser security settings were consolidated into one clear policy
  • FIXED A setting that allowed scripts to run dynamic code ('unsafe-eval') was removed
  • FIXED Broad permissions were narrowed to only allow connections to specific, known services (Power BI, Microsoft login)
  • FIXED The server no longer advertises what software it runs (hides X-Powered-By)

6.1 Content Security Policy — Where Content Can Come From

7. Audit Logging — Who Did What, and When

What this protects: Every important action in PRISM is permanently recorded: who logged in, who changed a data value, who approved a user, who changed a role. This means that if something goes wrong, you can trace exactly what happened, who did it, and when. It also deters misuse — people behave differently when they know their actions are recorded.

8. Database Security — Protecting Stored Data

What this protects: All utility data, user records, and configurations live in a PostgreSQL database. Several layers of protection ensure that database connections are never left open, queries cannot be tampered with, and simultaneous operations don't interfere with each other.

8.1 Connection Management

PRISM keeps a pool of pre-opened database connections and reuses them. This prevents connection leaks (where an abandoned connection stays open indefinitely). Every connection has a 30-second time limit — if a query takes longer than 30 seconds, it is automatically cancelled to free up resources.

8.2 Protection Against Query Tampering

All database queries use a tool (Drizzle ORM) that keeps user input separate from the query structure. This means someone cannot type malicious commands into a form field and have them executed as database instructions — the input is always treated as plain data, never as commands.

8.3 Preventing Conflicts Between Overlapping Operations

When multiple operations need to update the same thing at the same time (like two administrators editing the same KPI, or the rate limiter counting requests while others are incoming), PRISM uses a database feature that acts like a reservation token: only one operation can hold the token at a time. This prevents double-counting, data corruption, and race conditions.

// lib/ai/rate-limit.ts — atomic rate limit update
await db.execute(sql`SELECT pg_try_advisory_lock(4746)`);
// ... safely update the rate limit count ...
await db.execute(sql`SELECT pg_advisory_unlock(4746)`);

8.4 Password Storage

User passwords are never stored in plain text. Better Auth internally hashes every password using a cryptographic algorithm before storing it. Even if the database were compromised, the actual passwords would not be recoverable.

9. User Lifecycle — Registration to Deactivation

What this protects: Only approved people get accounts. External registrations go through a manual review. When someone leaves or their access is revoked, it stays revoked — deactivated accounts cannot be reactivated.

9.1 Registration Flow

  1. A person registers on the /auth page: enters name, email, organisation, role, datasets of interest, and reason for access.
  2. The system creates a pending user with a random password (used internally, never seen by the user).
  3. A magic link is sent.
  4. The user verifies their email by clicking the verification link.
  5. For external roles (EXT): The registration goes into a review queue. A DEV or BMO admin must manually approve or reject it.
  6. Once approved/verified: The user’s status transitions to active and they gain full access according to their role.

9.2 Status Transitions

A user’s account can be in one of three states, and transitions between them are strictly controlled:

Current StatusCan BecomeWho Can Change It
pendingactive or deactivatedAdmin (DEV/BMO)
activedeactivatedAdmin (DEV/BMO)
deactivatedCannot change—
The status rules run on the server — nobody can bypass them from their browser. Deactivated users stay deactivated permanently. This is intentional: once someone's access is revoked, it cannot be accidentally or maliciously turned back on.

9.3 Blocked Access Experience

Users with pending or deactivated status see a friendly blocked-access overlay explaining their status, rather than a confusing error page. They cannot access any protected area of the application.

11. Remaining Work & Next Steps

What this is: The code fixes are done, but a follow-up review (June 2, 2026) identified that PRISM needs ongoing processes — not just one-time fixes. This section covers what still needs attention and what management decisions are needed.

11.1 Top 5 Things Still Needed

PriorityWhat needs to happenBusiness impact
1 Prove that one utility cannot see another utility's data If this fails, confidential financial and operational data leaks between utilities — the biggest remaining risk
2 Extend two-factor authentication to cover all admin actions (not just selected pages) Currently, a stolen admin session could still access some sensitive functions
3 Actually test restoring from a backup Backups exist but nobody has verified they work. A backup you haven't tested is not a backup
4 Configure the server itself: firewall, traffic filtering (CDN/WAF), disable direct database access from the internet, disable root login The server is currently more exposed than it should be. These are one-time configuration changes on the server hardware
5 Create an ongoing security plan — not just one-time fixes Without regular reviews, testing, and clear ownership, security decays over time

11.2 Decisions Management Needs to Make

Before a full compliance plan can be created, leadership needs to answer these questions:

  1. Who uses PRISM? Is it internal-only? Sold to utilities as a service? Provided to donors?
  2. Where are users located? EU, UK, US, Pacific islands — this determines which privacy and security laws apply.
  3. Does PRISM handle personal data? If yes, privacy laws like GDPR may apply.
  4. Is PRISM a "product" under EU law? The EU Cyber Resilience Act takes effect September 2026 and applies to software products sold in the EU.
  5. What level of security assurance is needed? Formal certification (SOC 2, ISASecure)? Or internal best practices?
  6. How much risk is acceptable? What is the organization's tolerance for data exposure, downtime, or regulatory fines?
  7. Who decides? Which person or role can accept risk when something cannot be fully fixed?
