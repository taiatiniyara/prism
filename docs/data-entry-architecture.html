1. System Overview

The Data Entry module is the largest domain in PRISM. It enables Pacific utilities to input, review, and analyse benchmarking KPIs across report periods. The system supports three input modes — flat, grouped-by-generator, and grouped-by-payment-mode — with a cascaded calculation pipeline that automatically computes aggregated values and KPI formulas after each save.

3. Filter Context System

The data entry system uses a 6-axis filter context persisted in cookies (1 year TTL, httpOnly). When a parent filter changes, child filters are cascaded to null.

5. Three View Modes

The enter-data page renders one of three views based on subcategory context (conditional view logic in us3.conditionalViews.service.ts):

Flat Mode

Generic / Operational inputs

One row per input definition. Simple flat list with input cells for text, number, boolean, select, date, and managed lists.

inputRows.tsx inputCell.tsx

Used when: subcategory is NOT "Generation" and NOT "Tariff Structure"

Grouped by Generator

Generation inputs per energy resource

Inputs organized by energy resource (generator), showing all relevant input definitions for each generator entity.

generatorGroups.tsx

Used when: subcategory name equals "Generation"

Grouped by Payment Mode

Tariff inputs — two-level grouping

Two-level hierarchy: Payment Mode → Customer Type → input rows. Each customer type group has its own set of relevant input definitions.

tariffGroups.tsx

Used when: subcategory name equals "Tariff Structure"

View Mode Determination: The isGenerationContext(), isTariffContext(), and isOperationalContext() functions in us3.conditionalViews.service.ts match subcategory/category names from the database. The showServiceAreaSelector flag is set only when the category is "Operational".

Key Design Decisions

  • Multi-pass evaluation: up to MAX_PASS_MULTIPLIER = 2 times the number of targets — allows chained formula resolution
  • Status: each target is either calculated or skipped with a reason (missing-value, unknown-variable, evaluation-error)
  • All outcomes are persisted with a runId for audit trail
  • After aggregated worker completes, the KPI worker is triggered asynchronously

7. KPI Worker Pipeline

A 13-file async engine for KPI calculation with distributed locking, retry logic, and snapshot tracking. Public API exposed via app/data-entry/kpi-worker/index.ts:

index.ts

Public API:
triggerKpiWorker (async fire-and-forget)
triggerKpiWorkerAsync (await result)
listKpiWorkerStatuses (query status)

worker.ts

Main execution: orchestrates the full KPI calculation run for a given scope and trigger.

lock.ts

Distributed locking: acquireScopeLock prevents concurrent KPI recalculations for the same scope using PostgreSQL advisory locks.

resolveTargets.ts

Target resolution: determines which KPI targets need recalculation based on the changed inputs.

resolveInputs.ts

Input resolution: resolves formula input values from the data_entries table.

evaluator.ts

Formula evaluation: evaluates KPI formulas using resolved input values.

persistKpi.ts

Persistence: upsertCalculatedKpiValue — writes calculated KPI values back to DB.

retry.ts

Retry logic: exponential backoff for transient failures.

snapshot.ts

Snapshots: historical tracking of KPI calculation runs.

13. Cross-Cutting Concerns

Role-Based Access Control

proxy.ts middleware checks session + role before allowing access to /data-entry/*. Roles with data-entry access: DEV, BMO, BLO, CEO, DAOF, DAOH, DAOO (9 roles total). Scope resolution: global utility access vs org-scoped users.

Validation Rules

Built-in: data type, range min/max, polarity, mandatory fields ("N/A" toggle).
DEV builder: formula-based constraints, comparison operators, cross-field. Configured via dev_validation_* DB tables. Only shown to DEV role users.

Audit Trail

Every value change writes to data_entry_logs: previous value, new value, user ID, timestamp. Changes cascade: aggregated worker outcomes + KPI worker results are also git-like snapshotted.

Input Control Type Mapping

inputControlType.mapper.ts maps data types to UI controls:
text → text, number → number, boolean → boolean, select → select, date → date, managedLists → managedLists, fallback → text, gender → select

Relevance Filtering

Input definitions are filtered by relevance: input_relevance table determines which inputs show for which dimensions. is_relevant flag on individual data_entries rows. Irrelevant entries are excluded from UI and progress calculations.

Legacy Training Sync

input_dl_def_mappings tables bridge PRISM input definitions to legacy prism-training data definitions. /api/fact* and /api/dim* endpoints proxy to prism-training via PRISM_TRAINING_API_BASE_URL.
