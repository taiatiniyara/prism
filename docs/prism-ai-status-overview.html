PRISM AI — Status Overview

Technical summary for reviewers and stakeholders

Prepared 2026-09-16 · reflects lib/ai/, app/api/ai/, components/ai/, db/schema/ai.ts on branch fix-cross-utility-kpi-period-scoping, commit df2d896

PRISM AI is a Claude-powered chat assistant built into the PRISM platform that lets Pacific utility staff, managers, and executives ask performance and reporting questions in plain English and get grounded, sourced answers instead of digging through dashboards or spreadsheets.

It's live and in daily use. This report covers what it does, how it's built, how it decides what to trust, how it's kept safe and cost-controlled, what's changed recently, and what's left to do.

1. What It Does

PRISM AI is built on Anthropic's Claude models (Sonnet primary, Haiku as a cost/latency fallback), wired in through the Vercel AI SDK. Instead of a static dashboard, a user asks a question in their own words — "how's our SAIDI this year?" or "who hasn't submitted their data yet?" — and the assistant works out what's being asked, calls one or more of 69 specialised tools to fetch the real numbers, and answers conversationally, in the voice of a knowledgeable energy-sector advisor rather than a database readout.

It doesn't just recite figures: it's instructed to diagnose what a number means for a utility of that size, connect it to related metrics, benchmark it against targets and peers, and recommend a next step — while clearly separating stated fact from its own judgment (see §4). Answers stream in token-by-token, and while the assistant is working, the interface shows a live, plain-English list of what it's currently checking rather than a generic spinner.

3. How a Question Gets Answered

Every chat message goes through the same pipeline, entering at POST app/api/ai/chat/route.ts:

Origin + rate-limit + budget checks
→
Guardrail input scan
→
Load session + resolve data source
→
Build prompt + tool list
→
Model call (up to 10 tool-use steps)
→
Stream answer to browser
→
Persist turn + tool calls
  • Origin check — the request's browser origin must exactly match the configured app URL (a full parsed-origin comparison, not a simple prefix match, which closes a subdomain-spoofing gap a naive check would leave open).
  • Rate limit & budget are checked before the model is ever called, so a blocked request costs nothing (§9).
  • Audience register — the user's role (CEO, manager, external stakeholder, etc.) selects one of 7 tone/framing presets the prompt uses, so the same fact is explained differently to an executive than to a donor (§4). External users can self-declare their stakeholder type (government, consultant, donor, researcher).
  • Conversation summarization — once a conversation passes 8 exchanges, a cheap background model call condenses everything said so far (topics, key findings, which utility/period was discussed) into a compact summary that's reused on later turns instead of replaying the entire history — keeps long conversations fast and within the model's context limit.
  • Live progress streaming — the connection carries text, "thinking" narration, and tool start/end events on separate channels simultaneously, which is what powers the real-time "Checking your KPI submission status…" progress list instead of a static spinner.
  • Empty-answer recovery — in rare cases a tool-using turn can finish with no visible text (a known model/SDK edge case). The system detects this and silently retries once with a nudge to produce a final answer, invisibly to the user, before giving up.

4. Persona & Reasoning Style

The assistant's personality and rules live in a single large system prompt (lib/ai/prompt.ts, current version 2026-07-13-medallion-v2, roughly 9,000 tokens). Rather than a generic chatbot, it's instructed to behave as an "Energy Expert" for the Pacific Power Association. Key elements:

  • Conversational tone rules — no narrating its own process ("let me check Power BI…"), contractions allowed, varied sentence length, matches the user's energy level.
  • A 5-step reasoning chain — Diagnose → Connect → Position → Recommend → Caveat — which the chat interface renders as collapsible sections rather than a wall of text.
  • An opinion-safety rule — the assistant may offer judgment or a recommendation, but every opinion must be tied to a real retrieved number, clearly labelled as opinion (not fact), and hedged ("this strongly suggests…" rather than "you must…").
  • 7 audience registers — CEO/Executive/Board, Manager/Operations, Staff/Analyst, Government/Regulator, Consultant, Donor/DFI, and Education/Researcher — each shaping emphasis on the same underlying facts (a donor gets impact/value-for-money framing; a researcher gets method and data caveats up front).
  • A hard rule against confusing "submitted" with "performing well" — tools that check whether paperwork/data has been submitted must never be presented as if they were performance results. This is repeated explicitly in the prompt and covered by tests.
  • A fallback protocol for empty results — if the most recent period has no data, it's told to step back through the last 3–4 fiscal years/reporting periods before concluding there's a genuine data gap, rather than immediately reporting "no data."
  • An anti-injection clause — instructed never to reveal its own instructions or comply with "ignore previous instructions"-style requests, backed by a separate input-side filter (§8).
Prompt caching (live). Because the ~9K-token system prompt and the ~69 tool schemas are usually identical across every step of a multi-step answer, and often across turns within one conversation, they're marked for Anthropic's prompt caching. A cache hit skips reprocessing that fixed prefix, which is the main lever for getting the first word of an answer back faster on tool-using questions.

5. The Two Data Sources & How It Picks Between Them

The assistant can pull performance numbers from two independent places: PRISM's own database (a curated "gold layer" of computed KPIs), or a connected Power BI dataset queried live. Which one is treated as authoritative — and whether the other is used as a backup at all — is a setting an administrator controls, not something fixed in code.

SettingValuesWhat it controls
ai_primary_sourcewebapp | powerbiWhich source is tried first for every performance question.
ai_secondary_sourcewebapp | powerbi | noneWhether there's a fallback source at all (none = isolation mode, primary-only).

Both the instructions given to the model and the actual list of tools it's allowed to call are derived from this same setting, computed once per request — so the model can never be told to prefer one source while actually being handed tools for the other.

Isolation is enforced structurally, not just by instruction. When the secondary source is set to none, every tool belonging to the non-primary source is physically removed from the list the model sees before the request is sent — the team judged that relying on the prompt alone ("please don't use Power BI") was too leaky a guarantee for a hard boundary like this.

When a backup source is configured, the model follows a strict order: try the primary source; if it succeeds, stop there — it never cross-checks the other source for the same number. If the primary errors or comes back empty, it first tries nearby fiscal years/periods before falling back to the secondary source, and if both are genuinely empty, it says so honestly rather than substituting the wrong kind of data (e.g. submission status standing in for a performance number).

6. The 69 Tools

Tools are the assistant's only way of touching real data — it cannot query the database or Power BI directly, only through one of these 69 predefined, individually-scoped functions.

PRISM-native 39 tools

Administrative and workflow tools — review queue, submission/input status, KPI diagnostics, governance audit trail, custom KPI request status, guided data-entry help — plus a set of 6 direct performance tools that read PRISM's own KPI data (targets, correlation between KPIs, cross-utility comparison, compliance status, data quality, what-changed-since-last-time).

Power BI 30 tools

Schema discovery, live query execution against a catalog of pre-built templates, risk scoring, peer grouping, donor-report generation, renewable-energy and tariff scenario modelling, forecasting, correlation and anomaly detection, and deep-links back into the relevant Power BI report.

Both tool families sit on top of a large shared data layer (roughly 30 files) that does the actual database/DAX querying, benchmarking math, schema lookups, and a live integration with the World Bank's public API for country income classification and lending-category context (no API key needed).

Other notable capabilities

  • Visualization — the assistant can render its own answer as a table, bar chart, line chart, leaderboard, scatter plot, radar chart, sankey diagram, or heatmap, drawn client-side.
  • Export — answers can be exported straight to CSV or Excel via a dedicated export endpoint (§8 covers how that's kept safe).
  • Self-reporting — a user (or admin) can ask the assistant how much they've used it, and it answers from its own usage records.
  • Admin-gated tools — the governance-audit and platform-configuration tools are blocked outright for anyone who isn't a DEV or BMO-role user, enforced in code, not just by the prompt.

Plain-English tool narration

While the assistant works, it doesn't show raw function names — a translation table converts each tool into a present-tense description a non-technical user can follow (e.g. a risk-scoring tool becomes "Calculating a risk score from the Power BI data"). Any tool without an explicit translation still gets a readable auto-generated label rather than showing the internal name.

Known small gap: two real, callable tools (a World Bank context lookup and an input-field explainer) aren't yet listed in that translation table, so they currently fall back to a generic auto-formatted label ("Working on worldbank context") instead of a polished one. Cosmetic only — the tools work correctly — and it's a one-line fix once prioritised.

7. Reliability Engineering

All model calls funnel through one shared service layer, which layers several independent safety nets so that a hiccup in the AI provider doesn't become a visible failure for the user:

MechanismWhat it does
Automatic retryUp to 3 attempts with increasing delay (1s, 2s, 4s) for temporary failures (overload, timeout, rate-limited). A genuinely bad request (bad auth, malformed input) fails immediately instead of retrying pointlessly.
Model fallbackIf the primary model (Sonnet) is still failing after its retries, the whole request is retried against a second, faster/cheaper model (Haiku) with its own retry budget.
Circuit breakerIf a model fails 5 times in a row, calls to it are paused for 30 seconds (rather than continuing to hammer a struggling service), then automatically resume.
Empty-answer nudgeIf a turn that used tools somehow finishes with no visible text, one extra attempt is made with an instruction to produce a final answer before the system gives up.
First-response error checkBecause a streaming response can technically "start" before the model has actually produced anything, the system peeks at the very first piece of the response so a provider-side error can still trigger the retry/fallback logic, instead of silently reaching the user as a broken stream.
Context-length guardVery long conversations are automatically trimmed to fit the model's memory limit, with a small portion always reserved for the tool definitions; if a conversation truly can't fit, the user gets a clear "please start a new chat" message rather than a cryptic failure.
Extended "thinking" mode is currently switched off. Testing found that combining it with multi-step tool use produced blank final answers — the model's internal reasoning wasn't being carried through correctly across tool steps by the underlying SDK. It will only be re-enabled once that combination is independently verified to work.

8. Safety, Privacy & Security

Input filtering

Messages are scanned before they ever reach the model: email addresses, phone numbers, requests for private reviewer comments, credential/secret-sounding keywords, bulk-export phrasing, and known prompt-injection patterns ("ignore previous instructions", "reveal your system prompt", etc.) are all blocked. Messages are also capped at 4,000 characters.

Output filtering

The assistant's own response text is scanned again before it's shown or saved, stripping out any email addresses, phone numbers, or similar personal data it might otherwise echo back from something a tool returned.

Restricted tools stay restricted

The governance-audit and platform-configuration tools check the caller's actual role in code — a regular user cannot access them no matter how the question is phrased.

Origin validation

Every AI request is checked against an exact match of the app's configured URL, closing a subdomain-spoofing trick that a looser "starts with" check would have allowed.

Query injection protection

Before any AI-constructed query is sent to Power BI, it's sanitized and validated so a cleverly worded user prompt can't inject an arbitrary query.

Export safety

Exported CSV/Excel files have any cell that could be mistaken for a spreadsheet formula (starting with =, +, -, or @) neutralised, so opening an export can't trigger a hidden command. Row/column/cell-length limits and filename sanitisation are also applied.

Data stays within your organisation

By default, every tool scopes its results to the current user's own utility/organisation; a broader cross-utility comparison only happens when explicitly asked for. This is covered by its own dedicated test suite.

9. Usage Limits & Cost Control

Each question costs a small, real amount to process, so the platform enforces limits automatically, backed by the database (with an in-memory fallback if that write ever fails, so a limiting glitch fails open rather than blocking everyone):

  • Speed limits — a default of 20 requests per minute and 100 per 15 minutes, per person, so no single user (accidentally or otherwise) can overwhelm the system for everyone else.
  • Daily spending cap — each user has a daily budget (defaulting to $5.00, configurable). Once a user's estimated spend for the day hits that cap, further requests are blocked with a clear "$X of $Y used" message until it resets.
  • Cost estimation — every request's cost is estimated from real per-model pricing (the primary and fallback models are priced differently) and logged.
  • Admin usage dashboard — shows daily volume, per-user spend leaderboards, which tools are used most and how often they error, and how often the system had to fall back from the primary model to the backup one.
Backend-only today. The daily spending cap is fully enforced server-side — a user really is blocked once they hit it — but there's no visible cost indicator or "80% of your budget used" warning inside the chat window itself yet. A user who hits the limit is simply told to wait, without any earlier heads-up. This is the top item on the to-do list below.

10. What Gets Stored

Every conversation is persisted so it can be revisited, reviewed, and measured:

What's storedPurpose
ConversationsOne record per chat, auto-titled from the opening message, with a rolling summary once it gets long, and the ability to soft-delete.
Individual exchangesEach question-and-answer pair: which model answered, whether it had to fall back to the backup model, how long it took, and any error.
Tool callsEvery lookup the assistant made to answer a question — what it asked for, what came back, whether it succeeded, and how fresh/complete that data was.
FeedbackThumbs up/down on any answer, plus an optional written correction.
Review queueAnswers flagged (e.g. by negative feedback) for a human to review and mark approved, rejected, or needing revision.
Usage & cost metricsDaily per-user totals feeding the admin dashboard and the spending cap.

11. What's Changed Recently

Over the past two weeks, work has focused on making the assistant feel faster, clearer, and more trustworthy:

ChangeWhat it means for users
Plain-English tool narrationThe assistant now says things like "Checking your KPI submission status" while it works, instead of showing a technical function name.
Live progress displayUsers see, in real time, which step the assistant is currently on, instead of a generic "Thinking…" spinner.
Prompt caching enabledThe assistant's large system prompt and tool list are now cached between calls instead of reprocessed every time, speeding up answers — especially ones that need to look something up.
Better error diagnosticsWhen something does go wrong, the real underlying cause is now captured, which shortens how long any issue takes to fix.
Fixed a cross-utility comparison bugA tool for comparing a KPI across utilities was only checking one utility instead of all of them; this has been corrected.
Export & usage endpoints addedNew CSV/Excel export capability and a usage-reporting API, plus a fix ensuring rate-limit counters can't double-count under concurrent load.

Further back (over the prior few weeks): the "Energy Expert" persona and 5-step reasoning style were introduced, live World Bank country-data integration was added, the choice of primary data source became an admin-configurable setting rather than fixed in code, and the tool registry was split into clean, separately-maintained modules.

The audience shifts the framing, not the tool. The same question — e.g. "how are we doing?" — is answered differently depending on the asker's role: a CEO gets a decision-and-tradeoff framing, a donor gets impact and value-for-money, a researcher gets method and data caveats first. The underlying data lookup is identical; only the language around it changes.

14. Bottom Line

PRISM AI is live, actively used, and built on a solid technical foundation: 69 real tools across two independently-selectable data sources, layered reliability (retries, fallback model, circuit breaker), and concrete guardrails around privacy, security, and cost. 10 of 12 tracked improvement items are shipped. What remains is polish — a visible cost indicator and a prompt-size reduction — neither of which blocks day-to-day use.
